# Deployment details

## What install.sh writes

| Path | Contents |
|---|---|
| `/usr/local/bin/caddy` | Caddy with the plugin (`go build -tags http2legacy -trimpath`) |
| `/etc/systemd/system/caddy.service` | From [deploy/caddy.service](../deploy/caddy.service): runs as the `caddy` user, with only `CAP_NET_BIND_SERVICE` to bind low ports, and `GODEBUG=http2xconnect=1` |
| `/etc/caddy/Caddyfile` | The first line is `# Managed by caddy-network-relay deploy/install.sh`, followed by the domain and the first user. Mode 640, owned by `root:caddy` |
| `/etc/caddy/relay/` | Mode 700, only root can enter: the profiles (600), which contain the first user's password; it is stored nowhere else (delete them once installed). Installers before October 2026 also kept `<user>.password` here |
| `/var/lib/caddy/` | The `caddy` user's home directory; Caddy's certificates and ACME account are in `.local/share/caddy/` |
| `/var/www/relay/index.html` | The default website (not overwritten if it already exists). It can be replaced with any static website |
| `/etc/sysctl.d/60-caddy-network-relay.conf` | Raises the UDP receive and send buffer limits to 7.5 MB (quic-go's recommendation); limits that are already higher are left out |
| `/opt/caddy-network-relay/go/` | The Go used for building, from proxy.golang.org, verified against the hash in Go's checksum database (sum.golang.org); the hash is hard-coded in the script |
| `/var/cache/caddy-network-relay/` | Build cache, dependency modules, a backup from before each run (`backup.TIME/`), and the output of the latest self-check and configuration check |

It also: runs `apt-get install ca-certificates curl python3 iproute2`; creates the system user `caddy`; allows TCP 80, TCP 443 and UDP 443 when ufw is active; and with `--replace-network-relay` runs `systemctl disable --now network-relay`.

## The script's checks and rollback

- Before changing anything: the system version and architecture, the source directory, whether an existing Caddyfile was generated by this script, whether the apt caddy package is installed, whether the old Rust version is running, whether TCP 80/443 and UDP 443 are used by other programs, and (on a first install) whether the domain's A record points to this machine's public IP. If anything is wrong it exits without changing anything.
- The new binary first checks the configuration with `caddy validate`; if that fails, nothing is installed.
- If the service is not running after the start: the binary, Caddyfile and systemd unit from before the install are restored; on an upgrade the old version is started again, and on a first install the service is disabled and the generated configuration is removed. If a first install fails partway (before the service starts), the generated Caddyfile and password file are removed, so the next run is a first install again.
- If the service is running but the local self-check did not pass (most likely the certificate is not issued yet, or UDP is blocked): no rollback; it prints troubleshooting steps and exits with 1.

## Changing the domain

1. Add an A record for the new domain in DNS.
2. Edit `/etc/caddy/Caddyfile`: replace the old domain in the site address with the new one (`NEW_DOMAIN, :443 {`), and change the `# domain: OLD_DOMAIN` line at the top as well (the script uses it to recognize the install when upgrading).
3. `systemctl reload caddy`; Caddy obtains a certificate for the new domain automatically.
4. Regenerate the profiles with the new domain ("Regenerating the profiles" in the README, with the new domain in `--host`), remove the old one from each device and install the new one.

## Manual upgrade (a Caddy not installed by install.sh)

Build in the source directory, check the configuration, then replace the binary:

```bash
go build -tags http2legacy -trimpath -o caddy.new ./cmd/caddy
```

```bash
./caddy.new validate --config /etc/caddy/Caddyfile
```

```bash
install -m 755 caddy.new /usr/local/bin/caddy && systemctl restart caddy
```

(Adjust the paths to your installation.)

## Multiple users

One user per device: one `user NAME HASH` line per user inside `network_relay { }` in the Caddyfile. The install script only manages the first user's password file; you keep the other users' passwords yourself (or keep only their profiles).

## TLS client certificates

Caddy's `tls` directive can require and verify client certificates on both the
TCP and QUIC listeners. Use a dedicated relay listener with the same client
authentication policy on every accepted TLS connection policy. Sites with
different client certificate requirements must use separate listeners.

CONNECT names the destination in its HTTP authority, while TLS SNI names the
relay. Caddy automatically enables strict SNI/Host matching with client
authentication; this would reject CONNECT with 421. Explicitly configure the
relay listener for proxy authorities:

```caddyfile
{
	servers :443 {
		strict_sni_host insecure_off
	}
}

relay.example.com, :443 {
	tls {
		client_auth {
			mode require_and_verify
			trust_pool file {
				pem_file /etc/caddy/relay-client-ca.pem
			}
		}
	}
	network_relay {
		user iphone <password-hash>
	}
}
```

The relay rejects strict SNI/Host matching and mixed client-authentication
policies at provisioning, rather than accepting a configuration that cannot
proxy CONNECT or allows authentication through an unprotected SNI.

Provision a client identity on the Apple device, then generate its relay profile
with `--identity-certificate-uuid UUID`, using that identity payload's UUID.
The emitted `PayloadCertificateUUID` is inside the relay dictionary as required
by [Apple's relay payload schema](https://github.com/apple/device-management/blob/release/mdm/profiles/com.apple.relay.managed.yaml).
The identity payload is provisioned separately. It can complement Basic
credentials, or authenticate alone when the relay user has the matching
`certificate_sha256` fingerprint. Installed identity UUID references apply to
legacy profiles; DDM profiles use `--identity` and an identity asset instead.
With `NERelay`, configure `identityData` and its password instead.
The generated profiles use ordinary certificate trust. TLS raw public key
authentication (RFC 7250) is not implemented; leave `RawPublicKeys` unset.

## A port other than 443

Write the site address as `relay.example.com:8443, :8443`, allow that port for TCP and UDP in the cloud firewall, and add `--port 8443` when generating profiles and running the self-check. 443 is best: many networks only allow 443, and it looks like an ordinary website.
